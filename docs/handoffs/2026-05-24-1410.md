## 1. Issues reportados por Leo en playtest E2

### Issue A — Enemies de E2 no saltaban entre plataformas

Logs:
```
[ENEMY @-230,-0] no_jump: dx=383.1 > 250
[ENEMY @-264,-0] commit_edge: dir=1 (inter=(-300,-120) real_target=(153,-160))
```

**Diagnóstico:** Los enemies estaban usando `Platform1` **default** (-300, -120) como plataforma intermedia, no las override de E2. La AI los hacía oscilar en el lado izquierdo y nunca llegaban al player en el lado derecho.

**Causa raíz:** `enemy.gd._find_intermediate_platform()` busca candidatas con `get_tree().get_nodes_in_group("platform")`. Las plataformas default se ocultaban (`visible=false`) y se les deshabilitaba la colisión, pero **seguían en el grupo "platform"**. La AI las consideraba candidatas.

**Fix aplicado** (`world.gd._apply_platforms`):
- Cuando una plataforma default se oculta → `remove_from_group("platform")`.
- Cuando se muestra → `add_to_group("platform")`.
- Defensa en profundidad en `enemy.gd._find_intermediate_platform`: filtra `if not p2d.visible: continue`.

### Issue B — Rango de salto al filo

**Diagnóstico complementario:** Los layouts de E2/E3 que diseñé tenían dx centro-a-centro de 350 px, mientras `JUMP_TRIGGER_MAX_DISTANCE = 250`. Aun con el fix de Issue A, los enemies no podían cubrir los gaps.

**Fix aplicado:**
- `JUMP_TRIGGER_MAX_DISTANCE`: 250 → **290**.
- Layouts E2/E3 reajustados con dx ≤ 280 px entre plataformas (más fáciles de cubrir con salto multi-hop).

### Issue C — Arco / vara no disparan proyectiles

**Diagnóstico:** Al equipar arco o vara, el player seguía atacando cuerpo a cuerpo. `_start_attack()` solo activaba la hitbox melee sin importar el tipo de arma.

**Fix aplicado:**

1. **`projectile.gd`**: nuevo signal `hit_landed(target_hurtbox)` emitido tras conectar. Permite al shooter ganar Furia / Momentum al impactar.

2. **`player.gd`**:
   - Const `PLAYER_ARROW_SCENE` y `PLAYER_FIREBALL_SCENE` (preload de las mismas .tscn que usan Archer y Mage).
   - `_start_attack()` detecta `weapon.visual_type` del arma equipada:
     - `BOW` o `STAFF` → setea `_is_ranged_attack = true`.
     - Resto (Sword/Hammer/None) → melee como antes.
   - `_tick_attack()`: si es ranged, en lugar de activar hitbox, spawnea el proyectil una sola vez (al pasar `ATTACK_ACTIVE_START`).
   - `_spawn_player_projectile()`:
     - Bow → arrow scene. Staff → fireball scene.
     - Spawn position: `global_position + (20×facing, -45)` — altura del torso.
     - Daño = `hitbox.damage × MomentumSystem.damage_multiplier()`.
     - Dirección = `Vector2(current_facing, 0)` — horizontal hacia donde mira.
     - Suscribe `proj.hit_landed → _on_projectile_hit_landed → _on_hit_landed` para ganar Furia y Momentum igual que un melee hit.

## 5. Decisiones técnicas tomadas (sin preguntar)

1. **Add/remove del grupo "platform"** en lugar de solo `visible=false`. Razón: la AI usa `get_nodes_in_group()` que no filtra por visibilidad. Es la fix más limpia y de raíz.

2. **`JUMP_TRIGGER_MAX_DISTANCE 250 → 290`**. Pequeño aumento que mantiene la física consistente (con `JUMP_HORIZONTAL_SPEED=400` y vy=-850, en aire ~1.08s, el alcance horizontal teórico es ~432 px, pero la fase ascendente cubre ~216 px que es el target práctico). 290 es un margen razonable, no abusivo.

3. **Player projectile reuse de scenes existentes** (`projectile_arrow.tscn`, `projectile_fireball.tscn`). Mismo Projectile.gd, distinto `team`. Razón: evita duplicación de assets. El team=1 hace que el proyectil dañe a enemies (team=2).

4. **Spawn position del proyectil** del player: offset (20×facing, -45). Altura del hombro/mano frontal del StickFigure. Visualmente sale "de la mano".

5. **El daño del proyectil = `hitbox.damage × momentum_mult`** — mismo cálculo que el melee. PlayerStatsComponent ya tiene los stats del arma aplicados a `hitbox.damage`. Consistente entre melee y ranged.

6. **El proyectil dispara una sola vez por attack**, al pasar `ATTACK_ACTIVE_START`. Mismo timing visual que el swing del brazo. No spamea proyectiles dentro del mismo attack.

7. **Layouts E2/E3 reajustados** para que ningún dx entre plats > 290. Antes había gaps de 350 px que ni siquiera el threshold nuevo cubría. Ahora ≤ 280, con margen para que el multi-hop funcione.

## 6. Riesgos conocidos

⚠️ **Critical:**

1. **Si el bug de grupo persiste tras este fix**, puede ser por algún edge case del orden de `_ready`. Ej: si un enemy se spawnea ANTES de que `_apply_platforms` corra el remove_from_group, podría cachear referencias viejas. Pero como los enemies usan `get_nodes_in_group()` POR FRAME (no cache), no debería pasar.

2. **El proyectil del player tiene `team=1`** (igual al player). El `_on_area_entered` del projectile compara `hurtbox.team == team` y descarta. Eso significa que si un proyectil del player choca con el hurtbox del PLAYER (no posible normalmente, pero si rebota o algo), NO le hace daño. ✓ correcto.

⚠️ **Medium:**

3. **Si el player camina hacia atrás mientras dispara**, el proyectil ya está spawneado con `current_facing` del momento del spawn. Si girás justo después, el proyectil va por su lado. Esperado, pero notar.

4. **La fireball del Mage usa la MISMA scene** que el player con vara. Si Leo cambia colores del fireball para distinguir "fuego enemigo" vs "fuego player", afectará a ambos. Solución futura: 2 scenes distintas o tint propio.

5. **El daño se calcula al spawnear el proyectil**, no al impactar. Si el Momentum sube ENTRE spawn y hit, el daño no incluye el aumento. Consistente con la lógica del Archer/Mage (mismo timing).

⚠️ **Low:**

6. **El swing visual del brazo sigue siendo el mismo en ranged y melee**. Para el arco, idealmente sería "tensar y soltar" no "barrer espada". Lo dejo para futuro pulido.

## ADDENDUM — 13:40 — Bug AI: salto en dirección opuesta al target

### Diagnóstico

Logs tras el fix de grupos mostraron enemies oscilando entre x=-160 y x=-210, no llegando a Plat_e2_a. El bug raíz:

1. Enemy debajo del shadow de Plat_e2_a → `_has_ceiling_above() = true`.
2. `_should_commit_to_edge()` retorna `+1` (escapar por la derecha del shadow porque player real está a la derecha).
3. `_apply_facing(+1)` → `current_facing = +1`.
4. `_try_reactive_jump()` chequea que puede saltar a Plat_e2_a (-500, -90), pero NO actualiza facing — solo `velocity.y = JUMP_VELOCITY`, `velocity.x = 0`.
5. Next frame, en aire con `current_facing = +1`. `velocity.x = +1 * JUMP_HORIZONTAL_SPEED * air_factor = +400`.
6. **Vuela a la DERECHA aunque Plat_e2_a está a la IZQUIERDA**. Cae sin alcanzar.
7. Loop.

### Fix aplicado

`enemy.gd._try_reactive_jump()`: justo antes de `velocity.y = JUMP_VELOCITY` en AMBOS paths (gap jump + regular jump), forzar `_apply_facing(target_dir)` donde `target_dir = sign(effective.x - global_position.x)`.

```gdscript
var jump_facing: int = int(sign(effective.x - global_position.x))
if jump_facing != 0 and jump_facing != current_facing:
    _apply_facing(jump_facing)
velocity.y = JUMP_VELOCITY
velocity.x = 0.0
```

Esto garantiza que en aire el enemy vuela hacia el effective target — independiente de lo que `commit_edge` o `_decide_chase_direction` hayan decidido segundos antes.

### Validación esperada

Si después de este fix los enemies todavía no alcanzan al player en E2/E3:
- Confirmar que los layouts permiten cadena de saltos (cada plat alcanzable desde la anterior con dy ≤ 145 y dx ≤ 290).
- Si caen del lado correcto del Plat_e2_a tras saltar, deberían poder seguir A→B→C→D.

## ADDENDUM #2 — 14:10 — Bug AI: enemies en suelo no escalan a plats altas

### Diagnóstico

Player parado en Plat_e2_c (60, -240). Enemies en el suelo a x≈25, y=0 con dy_above=250 al target. `MAX_JUMP_HEIGHT*1.05 = 152` → no saltan.

`_find_intermediate_platform()` no devuelve ninguna plat porque:
- Plat_e2_a (-500, -90) alcanzable desde suelo (dy=90 ≤ 145), pero filtro 3 la descarta: `jump_to_target = -90 - (-260) = 170 > 159.5` (desde A no se alcanza el target directo).
- Plat_e2_b, _e2_c, _e2_d: todas tienen dy_above > 145 desde el suelo → filtro 1.

Resultado: `_intermediate_platform = null` → effective target = player real → enemy intenta saltar directo dy=250 → "físicamente imposible".

### Fix aplicado: gradual climb (multi-hop iterativo)

`_find_intermediate_platform()` ahora hace **2 pasadas**:

1. **Estricta**: intermedia DEBE permitir saltar al target directo (filtros 1, 2, 3, 4, 5). Igual que antes.
2. **Relajada**: si la estricta no encuentra → reintenta sin filtros 3 y 4. Acepta cualquier plat alcanzable desde el enemy (filter 1, 2, 5).

Permite "escalada gradual": el enemy salta a la plat más alta que pueda, en la siguiente iteración busca de nuevo, y así sucesivamente.

```gdscript
func _find_intermediate_platform() -> Node2D:
    if _target == null:
        return null
    var strict: Node2D = _find_intermediate_internal(true)
    if strict != null:
        return strict
    return _find_intermediate_internal(false)
```

### Validación esperada

Con la cadena de E2 (suelo → A → B → C → target):
- Enemy suelo → busca strict (null) → busca relajada (Plat_e2_a) → camina hacia x=-210 → salta a A.
- En A → busca strict (Plat_e2_b alcanza target con dy 80) → salta a B.
- En B → busca strict (Plat_e2_c bloqueada por filter 4) → busca relajada (Plat_e2_c) → salta a C.
- En C → multi_hop_active desactivado → chase normal → ataca al player.

### Si todavía no escalan

Posibles causas:
- Los enemies oscilando antes de llegar al lado de Plat_e2_a por commit_edge / chase conflict.
- Algún enemy queda atrapado en aire y no aterriza.
- Telegraph muy largo durante el escalado y el player se aleja antes.
